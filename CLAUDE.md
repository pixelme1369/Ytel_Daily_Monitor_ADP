# CLAUDE.md

## Project

Vanilla JS call center dashboard suite — no framework, no build step.
SheetJS 0.18.5 + Chart.js 4.4.0 + jsPDF 2.5.1 + JSZip 3.10.1 via CDN.

| File | Purpose |
|------|---------|
| `Ytel_Daily_Monitor_v2.html` | The dashboard (production) — sidebar nav, date range, export CSV, role editor |
| `Agent_Performance_Range.html` | Standalone agent performance report with date range picker |
| `command-center/index.html` | Independent Ytel-only ops dashboard ("Dialer Command Center") — see its own section below |

The original single-date dashboard (`Ytel_Daily_Monitor_ADP.html`) was removed in July 2026 — v2 is the only dashboard. Any older doc/commit references to "both dashboards" or "the original" refer to that deleted file.

## Design System

`DESIGN.md` (added August 2026 via `/design-consultation`) is a **proposed** redesign of `Ytel_Daily_Monitor_v2.html` — typography (Geist replacing Inter), a severity-tint addition to the existing color semantics, a workflow-choreographed navigation reorder, and a 9-card-to-3-card consolidation plan. **It has not been implemented.** The live dashboard still uses Inter and today's card ordering/count; do not assume anything in `DESIGN.md` is already true of the current code. Always read `DESIGN.md` before making any *new* visual or UI decision so proposal and implementation stay coherent as pieces of it land — do not deviate from it without explicit user approval, and do not silently apply it wholesale either; each piece (font swap, IA reorder, card consolidation, severity tint) is its own separate change per the "minimum necessary change" rule below.

## Dialer Command Center (`command-center/index.html`)

Added July 2026. A **completely independent** dashboard — its own file, own dark "ops center" visual design, own script from scratch. It does **not** share code, functions, CSS, or localStorage keys with `Ytel_Daily_Monitor_v2.html` / `Agent_Performance_Range.html` (localStorage keys are prefixed `dcc_` to avoid collision). Treat it as a separate product that happens to live in the same repo — changes to v2 should not be assumed to apply here and vice versa.

**Why it exists**: v2 and Agent Performance Range both assume a Ytel export merged with CRM columns (`Cordoba Enrolled Date`, `CRM Status`, `Assigned To`, `Enrolled Debt`, `State`/`CRM_State`). This dashboard analyzes a **raw Ytel-only export** — call detail records with no CRM columns at all. Every feature that depends on enrollment/conversion (Enrolled KPI, Debt, Conv%, CA Escrow pending-deal logic, Ytel Discrepancy) is dropped entirely rather than approximated, since without CRM data there is no ground truth for "did this lead close."

**Sections**: Overview KPIs (Total Calls, Unique Numbers Received [inbound-unique — the user only cares about inbound volume here; outbound detail lives in the Agent Performance table], Contact Rate (outbound) [unchanged — % of unique outbound-dialed numbers reached >30s, deliberately kept outbound-scoped even though the received-numbers tile switched to inbound], Avg Talk Time, Drops, DNC Calls, Dialed After DNC) · Issues Detected (compliance/ops alerts, not conversion-based) · Call Volume/DNC/Drops by hour charts · Disposition Breakdown · Agent Performance table (talk-time brackets, inbound/outbound, drops, redials — no Enrolled/Debt/Conv% columns) · Agent Rankings (by volume / contact rate / drop rate — conversion ranking removed) · **Agent Scorecard** (one visual card per agent — call count, avg talk, drop rate, a talk-time bracket bar [≤30s dead / 30s–5min / 5–20min / 20min+, from `agentMap[name]`'s `short`/`r2m`/`r2to5`/`r5to10`/`r10to15`/`r15to20`/`r20to30`/`gt30` fields], and a color-coded verdict badge — see below) · Campaign/Queue Breakdown (Contact% only, no Enrolled column) · Top 5 Numbers · VDCL/VDAD Analysis · Missed Callbacks (TIMEOT, single list) · DPC Drops Never Called Back (single list) · Incomplete Transfers + Correct Transfers Received (counts only) · Openers Transfer Breakdown + Lowest Transfer Rate ranking · **Long Calls, No Follow-up** (renamed from v2's "Long Calls, No Deal" — flags a phone if no call from *anyone* occurs after the qualifying long call, per the phone's full call timeline in `window._phoneAllCalls`, rather than checking against enrollment) · Settings (role editor for Closers/Openers/Retention, alert thresholds).

**Known v1 gaps** (flag to the user if asked, don't silently claim otherwise): agent-level opener transfer-rate rounding uses the same bracket data as the breakdown table (accurate); redial threshold in Settings (`TH.redials`) is not yet wired 1:1 to the redial-flag count shown in Issues Detected (issue text uses a coarser `heavyRedialAgents` cutoff, not the exact threshold value) — cosmetic, not a correctness bug, but worth tightening if this dashboard gets real usage.

Deployed to Vercel as a **separate project** (`ytel-dialer-command-center`, own domain) from the `ytel-daily-monitor` project that serves v2 — both build from the same `main` branch, so the file lives at `command-center/index.html` (moved out of the repo root in July 2026 for exactly this reason) instead of alongside the other dashboards. The command-center Vercel project has its **Root Directory** set to `command-center` in its project settings, which scopes it to only that folder's files — so `/` on its domain serves `index.html` directly with no `vercel.json` rewrite needed, and it can't collide with or affect the root `vercel.json` that the `ytel-daily-monitor` project (Root Directory `.`, whole repo) uses to route `/` to `Ytel_Daily_Monitor_v2.html`. If this dashboard ever needs its own `vercel.json` (headers, additional rewrites, etc.), add one inside `command-center/` — it will only apply to that project, not to `ytel-daily-monitor`.

### Data Source: BigQuery (not file upload)

Added July 2026. This dashboard no longer has a file-upload UI — it is the **one exception** in this repo to the "no framework, no build step" rule at the very top of this doc, since a serverless API route was required to query BigQuery securely (a client-side page can't hold BigQuery credentials without exposing them to anyone who views source).

- **Table**: `amity-one-debt-sys.aod_ytel_call_log.call_log` — same column names as the old CSV/XLSX export (`call_date`, `direction`, `phone_number_dialed`, `status`, `status_name`, `user`, `full_name`, `campaign_id`, `source_id`, `length_in_sec`, `recording_location`), so `normalize()` in the frontend needed zero changes when this was wired up. `call_date` is a BigQuery `DATETIME` column (confirmed via the working `n8n` query this replaced, which compares it against `DATETIME(...)` literals) — meaning it's already naive wall-clock time with no timezone attached, exactly like the old CSV/XLSX `call_date` strings. **Do not add timezone conversion** (e.g. `FORMAT_TIMESTAMP` with a zone) to the query or the hour-of-day charts will shift.
- **API route**: `command-center/api/calls.js` (Vercel serverless function, Node.js, CommonJS — matches the style of the root `api/upload.js`/`api/latest.js`). Accepts `GET /api/calls?from=YYYY-MM-DD&to=YYYY-MM-DD`, runs a parameterized query scoped to that date range (`from` 00:00:00 inclusive through the day after `to` 00:00:00 exclusive), selects only the columns the frontend actually uses, and returns `{rows: [...]}`. `command-center/package.json` declares the `@google-cloud/bigquery` dependency (Vercel needs a `package.json` inside the project's Root Directory to install serverless function dependencies — the repo-root `package.json`, used by the `ytel-daily-monitor` project's blob-storage API, is out of scope for this project since Root Directory is `command-center`).
- **Credentials**: a GCP service account key (JSON), stored as the `GCP_SERVICE_ACCOUNT_KEY` environment variable on the `ytel-dialer-command-center` Vercel project (Production scope), **never committed to the repo**. The API route parses it with `JSON.parse(process.env.GCP_SERVICE_ACCOUNT_KEY)` and authenticates via `client_email`/`private_key`.
- **Frontend flow**: `runAnalysis()` is now async — it disables the Run Analysis button, shows a loading state, calls `fetchCalls(from, to)` (a thin `fetch('/api/calls?...')` wrapper), normalizes the returned rows the same way the old file-upload path did, and caches them in `mergedRaw`/`lastFromStr`/`lastToStr`. Changing a role or threshold in Settings calls `rerunIfLoaded()` instead of re-running the fetch — it rebuilds `buildDashboard()` from the already-cached rows so editing Settings doesn't re-query BigQuery every time. The date pickers default to **today** on page load (`setDefaultDateRange()` in INIT) since there's no uploaded file to infer a date from anymore.
- Every request re-queries BigQuery — there's no row cap in the query, so a very wide date range on a busy table could be slow/costly. Not yet an issue at normal daily-range usage; worth adding a max-range guard if this gets used for month-long pulls.

### Agent Scorecard

Added July 2026, card `#sec-scorecard` (`renderAgentScorecard()`), right after Agent Rankings. Built for a dialer manager doing at-a-glance agent monitoring — one card per agent instead of a table row, sorted by call volume descending.

- **Bracket bar**: 4 buckets, not the full set of brackets Agent Performance tracks — `≤30s dead` (`short`), `30s–5min` (`r2m+r2to5`), `5–20min` (`r5to10+r10to15+r15to20`), `20min+` (`r20to30+gt30`) — each segment's width is its % share of the agent's total calls. `r2to5` (2–5min) is a field added to `agentMap` specifically for this — it didn't exist before (the per-row accumulation loop had a documented gap: `else if(r._sec<300){}`, meaning 2–5min calls counted toward `total` but weren't tracked in any bracket field at all) and nothing else reads it, so this was purely additive.
- **Verdict badge** (`scorecardVerdict()`) — the answer to "is this agent's time paying off," using only call-behavior signals since Command Center has no CRM/enrollment ground truth:
  - **Openers**: same transfer-rate formula as the "Lowest Transfer Rate" ranking (`trns/calls` summed over the same >2min brackets) — `<15%` red "Struggling to transfer", `15–30%` amber "Average transfer rate", `≥30%` green "Strong opener". An opener with zero calls >2min shows a neutral "No calls >2min" badge instead of a misleading 0%.
  - **Everyone else** (closer/retention/unassigned): reuses `computeLongNoFollow()` (the same function backing the Long Calls, No Follow-up card) at a **fixed 1200s (20min) threshold**, independent of whatever the Long Calls card's own dropdown is set to, so the scorecard doesn't silently change meaning when someone changes that selector. Needs ≥2 qualifying long calls to score: `<25%` no-follow-up rate → green "Efficient — long calls land", `>60%` → red "Long calls, low follow-up", else amber "Average follow-up rate". Agents with fewer than 2 long calls fall back to a drop-rate check (`>1.5×TH.dropPct` → red "High drop rate") or a neutral "Not enough long calls to score" badge.
- `computeLongNoFollow(name, b, thresh)` was extracted as a shared top-level function (previously inlined in `renderLongNoFollow()`) specifically so the scorecard could reuse the exact same long-call/follow-up logic at its own fixed threshold without duplicating it — `renderLongNoFollow()` itself is unchanged in behavior, still driven by the `#longThreshold` dropdown.

## v2 Dashboard (`Ytel_Daily_Monitor_v2.html`)

### Data Source: Live BigQuery Merge (default), file upload kept as fallback

Added July 2026. v2 no longer requires uploading a pre-merged Ytel+CRM export to run a report — by default it queries BigQuery directly for the selected date range and merges Ytel call data with CRM lead data server-side, mirroring the same "CRM-to-Ytel-Merging" logic the user previously ran manually before uploading. File upload (`handleMerged()`) and "Load Shared Data" (`loadSharedData()`, the password-protected Vercel Blob path) are both kept exactly as they worked before — if either populates `mergedRaw`, that upload takes over as the data source until "Clear" is clicked, since a manually uploaded file is trusted as an explicit override.

- **API route**: `api/merged-calls.js` (Vercel serverless function, Node.js, CommonJS, same shape as `command-center/api/calls.js`). Accepts `GET /api/merged-calls?from=YYYY-MM-DD&to=YYYY-MM-DD`. Two BigQuery queries, same client/credentials:
  1. Ytel call log — identical table/columns/date-range logic to `command-center/api/calls.js` (`amity-one-debt-sys.aod_ytel_call_log.call_log`, `call_date` is a naive-wall-clock `DATETIME`, no timezone conversion).
  2. CRM leads — `amity-one-call-data.aod_forth_data.VW_SAMAN` (different GCP project than the Ytel table, both reachable with the same `GCP_SERVICE_ACCOUNT_KEY` service account — confirmed it has access to both). A lead can own up to 4 phone numbers (`phone`, `phone2`, `phone3`, `phone4`), so the query matches any of the day's dialed numbers against any of those 4 columns. Matching is done on the **last 10 digits, non-digits stripped** (`REGEXP_REPLACE(...,  r'[^0-9]', '')` in SQL, `normPhone()` in JS) since the Ytel and CRM phone formats aren't guaranteed to match exactly (dashes, `+1`, parens). Only queries CRM for phones that actually appear in that day's Ytel batch (`WHERE phone IN UNNEST(@phones) OR phone2 IN UNNEST(@phones) OR ...`) rather than pulling the whole CRM table every request.
  - Output rows are the Ytel call fields plus exactly the 6 CRM columns v2's JS actually reads (matches the "Key Columns Expected in XLSX" table below): `CRM Status` (← `status`), `Enrolled Debt` (← `enrolled_debt`), `Cordoba Enrolled Date` (← `cordoba_enrolled_date`), `Assigned To` (← `assigned_to`), `State` (← `state`), `Credit Score` (← `credit_score`, added August 2026 for the CRM Status Breakdown card's Credit Pulled filter — see below). `Last Credit Pulled Date`/lead `id` from the CRM view are still not fetched — nothing in v2 consumes them; add them later if a future report needs them.
  - `command-center`'s `package.json` already declares `@google-cloud/bigquery`; the repo-root `package.json` (used by this route, and by `api/upload.js`/`api/latest.js`'s `@vercel/blob`) now declares it too.
- **Credentials**: reuses the same `GCP_SERVICE_ACCOUNT_KEY` env var pattern as command-center — must be set on the `ytel-daily-monitor` Vercel project (Production scope) for this route to work; the service account needs BigQuery read access to both `amity-one-debt-sys` (Ytel) and `amity-one-call-data` (CRM).
- **Frontend flow**: `runAnalysis(force)` is now async. `usingUploadedFile` (set `true` by `handleMerged()`/`loadSharedData()`, reset by `clearAll()`) decides the data source: if a file was uploaded, the pre-existing synchronous logic runs completely unchanged (filters the whole uploaded `mergedRaw` by date range client-side, same as always). Otherwise, `runAnalysis()` calls `fetchMergedCalls(from, to)` (a `fetch('/api/merged-calls?...')` wrapper) and replaces `mergedRaw` with the live-merged rows for that exact range — skipped if `lastLiveFromStr`/`lastLiveToStr` already match the current picker values **and `force` is falsy**, so Settings-triggered re-runs (`saveRoles()`/`saveThresholds()`, which call plain `runAnalysis()` when `mergedRaw` is truthy) rebuild from the cached fetch instead of re-querying BigQuery on every threshold tweak. The date pickers already defaulted to today on page load (pre-existing INIT code) — this is what makes "load today, no upload" the default path in practice.
- **Bug fixed (July 2026): clicking "Run Analysis" again for the same date range silently served stale cached rows, including stale `recording_location`.** The `lastLiveFromStr`/`lastLiveToStr` cache-skip check didn't distinguish an explicit user re-run from an internal Settings-triggered rebuild — so if a call's `recording_location` (or CRM Status) populated in BigQuery *after* the first fetch for a given day (a real gap: recordings often finish uploading/transcoding a few minutes after the call ends), re-clicking "Run Analysis" for that same range never re-queried BigQuery, and the dashboard kept showing "No recording available" even once BigQuery had the URL. Fixed by adding a `force` param to `runAnalysis(force)`: the sidebar "Run Analysis" button and the `Today`/`Yesterday`/`WTD`/`MTD` quick-range pills now call `runAnalysis(true)`, which always re-queries regardless of the cached range; `saveRoles()`/`saveThresholds()` still call plain `runAnalysis()` (no force) so a role/threshold tweak keeps rebuilding from the already-cached rows instead of re-hitting BigQuery. `command-center`'s `runAnalysis()` was already unaffected by this bug — it has no such cache-skip guard and always re-queries on every click.
- Because CRM enrichment reflects each phone's *current* CRM state (not a snapshot frozen at export time), the existing "look across the whole uploaded file" business logic (`realEnrolledPhones`, `phoneIsCA`, `anyEnrolledPhone`) still works correctly against live-fetched rows without querying extra historical days — a phone's real `Cordoba Enrolled Date`, if one was ever set, comes back on every row for that phone in the current range regardless of when the enrollment actually happened.
- Every request re-queries BigQuery — no row cap on the Ytel query, same caveat as command-center: a very wide date range on a busy table could be slow. Not an issue at normal daily/weekly usage.
- **Bug fixed (July 2026): CRM phone columns are `FLOAT64`, not `STRING`.** `VW_SAMAN`'s `phone`/`phone2`/`phone3`/`phone4` columns are numeric in BigQuery, not text — the original query's `IFNULL(phone, '')` threw `No matching signature for function IFNULL ... {DOUBLE, STRING}`. Fixed by going through `CAST(SAFE_CAST(phone AS INT64) AS STRING)` before the last-10-digits `SUBSTR` comparison (INT64 first so no stray `.0` decimal ends up in the digit string; `SAFE_CAST` so a column that turns out not to be cleanly numeric degrades to no-match instead of erroring the whole query). No `REGEXP_REPLACE` needed on this side — a genuinely-numeric column can't contain dashes/parens/`+1` in the first place, so the JS-side `normPhone()` remains the only place doing digit-stripping (needed for the Ytel side, which is a real formatted string).
- **Bug fixed (July 2026): startup auto-load of the shared file silently blocked live BigQuery.** INIT used to call `loadSharedData(true)` unconditionally on every page load — a pre-BigQuery feature that pulled whatever file was last pushed to the password-protected Vercel Blob via `upload.html`, so every viewer saw the same data without re-uploading. Once that succeeded, it set `usingUploadedFile=true`, which permanently locked `runAnalysis()` into the old client-side-filter path for the rest of the session — so picking today's date and clicking Run Analysis just filtered the stale uploaded file (finding zero calls, "No calls found in that date range") instead of ever querying BigQuery, with no indication why. Fixed by removing the automatic `loadSharedData(true)` call from INIT entirely.
- **Bug fixed (July 2026): sidebar decluttered — Copy Summary and Load Shared Data buttons removed.** Per user request the two buttons are gone from the sidebar (`copySummary()`/`loadSharedData()` are still defined but now unreferenced by any UI element — left in place rather than deleted, cheap to re-wire a button to them later if wanted). The upload dropzone also moved from a large 3-line box at the top of the sidebar to a compact one-line `.sb-drop-mini` pinned near the bottom (`.sb-upload-mini`, `margin-top:auto` inside the flex-column `.sb-inner`) — same `#mergedCard`/`#mergedFile`/`#mergedName`/`#mergedStatus` IDs, so `handleMerged()` and the drag/drop wiring are untouched.
- **Empty-state copy updated (July 2026)**: `#emptyState` used to say "Upload your merged file to get started" — stale once live BigQuery became the default (no upload required). Now shows the app's name ("Ytel VS CRM", matching the sidebar logo) as the headline with copy pointing at Run Analysis / the quick-range buttons instead of uploading.
- **Bug fixed (July 2026): Dialed-After-DNC issue row's badge overlapped its buttons.** `.issue` is a 3-column CSS grid (`4px 1fr auto`). The `afterDnc` row rendered 3 trailing siblings — "View Numbers" button, "Export CSV" button, and the severity badge — as separate grid children with no 4th column to place them in, so the grid auto-wrapped the overflow into a broken implicit row that visually collided with the badge. Fixed by wrapping all trailing actions (any `exportDnc`/`afterDnc` buttons + the badge) into one `flex-direction:column` container, so they always occupy exactly the grid's 3rd column and stack vertically — "View Numbers" above "Export CSV" above the badge, no overlap regardless of how many buttons a given issue type has.
- **Last updated indicator**: `#lastUpdated` span in the Overview section header (`.card-title-sub`, next to the "Overview" title) shows `Data as of <time>` — set at the end of `runAnalysis()` right after `buildDashboard()` returns, using the browser's wall-clock time at that moment (not a server timestamp), so it reflects when the currently-displayed data was actually fetched/rebuilt, whether from live BigQuery or an uploaded file.
- **Quick date-range buttons**: `Today` / `Yesterday` / `WTD` / `MTD` pills (`.qd-btn`) above the From/To fields — `setQuickRange(kind)` computes the range client-side (WTD = Monday of the current week through today; MTD = 1st of the current month through today), fills `fromDate`/`toDate`, highlights the clicked button (`.active`), and immediately calls `runAnalysis()`. Manually editing either date input clears the highlight (`input` listener in INIT) so a stale-looking active button never lies about what's actually selected. `qd-today` starts highlighted on page load to match the default date range, without auto-running analysis (that still requires an explicit click/button press, consistent with not re-querying BigQuery on every page view).

### Layout
Left sidebar (220px fixed) + main content area. Sidebar contains: logo, file upload drag-drop zone, `fromDate`/`toDate` pickers, Run Analysis button, and nav links.

**Auto-hide on mouse leave**: `#sidebar` collapses to a 14px rail when the mouse leaves it (250ms delay via `initSidebarAutoHide()`, called from Init), giving the dashboard the reclaimed width — `.sidebar` animates `width`/`min-width` (240px ↔ 14px) via CSS transition; its actual content lives in a fixed-240px `.sb-inner` wrapper so nothing squishes mid-transition, just clips under the outer `overflow:hidden`. Hovering the rail (`mouseenter`) or dragging a file onto it (`dragenter`) re-expands it. Not persisted — always starts expanded on load. Desktop-only in effect — see the mobile behavior below, which neutralizes `.collapsed`'s width change since visibility there is driven by `.mobile-open`/`transform` instead.

**Mobile (≤768px): off-canvas sidebar, not the desktop auto-hide rail.** Added July 2026 — on a phone-width viewport the sidebar used to render at full 240px next to the content every time (no hover-driven collapse, since there's no mouse), squeezing the dashboard into a sliver. Fixed with an off-canvas pattern: `#mobileMenuBtn` (a `☰` button, fixed top-left, only `display:flex` inside the `@media(max-width:768px)` block) calls `toggleMobileSidebar()`; `#sbScrim` is a full-screen dark backdrop (`closeMobileSidebar()` on click). Inside that breakpoint `.sidebar` becomes `position:fixed` and starts off-screen (`transform:translateX(-100%)`), sliding in via the `.mobile-open` class; `initNav()`'s link-click handler calls `closeMobileSidebar()` after scrolling to a section so tapping a nav link also closes the menu. `env(safe-area-inset-top)` is used for the button's top offset and the sidebar's/content's top padding so the button and content clear the iOS notch/status bar (`viewport-fit=cover` added to the `<meta name="viewport">` tag, required for `env()` to report non-zero on iOS). Above 768px none of this applies — the existing hover auto-hide behavior is unchanged.

| Unique Calls >2 Min | KPI tile (Overview grid, next to Contact Rate) = count of unique phones whose longest call in the range exceeded 120s — `gt2mUnique = Object.values(phoneBest).filter(s=>s>120).length`, same `phoneBest` per-phone-max-seconds map used by Contact Rate/`>15 Min`/`>30 Min`/`>45 Min`; subtitle shows `% of unique calls` (of `uniquePhones`), same convention as the other duration KPI tiles |
| ~~Copy Summary~~ | Removed from the sidebar (July 2026, see Bug Fixed note above) — `copySummary()` still builds a text digest from `window._summary` if ever re-wired to a button, but nothing currently calls it |
| Data-quality warning | `runAnalysis()` counts rows whose `call_date` can't be parsed (`badDateRows`) — shown in the sidebar hint + toast so a malformed export can't silently shrink the numbers |
| Auto date range | After upload, `autoSetDate()` sets `fromDate`/`toDate` to the **newest** day in the file (it previously wrote to `targetDate`, an element that only existed in the deleted original dashboard, and threw) |
| Collapsible sections | Each card has ▼/▶ toggle; state persisted in `localStorage` keyed `collapse:<sectionId>` |
| Multi-file upload | Merged into `mergedRaw[]` — analyze data from multiple XLSX files at once |
| Ytel Discrepancy | KPI tile = count of unique phones with a `status==='SALE'` row where **no row for that phone** has a `Cordoba Enrolled Date`/`Enrolled Date` (reuses `anyEnrolledPhone`, the same per-phone enrollment-presence Set used by DPC/Incomplete Transfers/Received Transfers) — a dialer-side "sale" that never made it into the CRM as an enrollment; phones kept in `window._saleDiscrepancyPhones`, CRM status per phone (from the SALE row's `r._crmStatus`, first non-empty wins) kept in `window._saleDiscrepancyCrm`; clicking the tile opens the shared enroll modal (`showSaleDiscrepancyPhones()`, phone list with a CRM status pill next to each number, same modal as `showEnrolledPhones`) |
| Agent Report Cards | Bottom section `#sec-report-cards` (nav link "Agent Report Cards") — card `#reportCardsCard` with a single button "⬇ Download All Agent Cards (ZIP)" → `exportAgentReportCards()`. **Closers only** — `rows` filters `window._agentAllRows` to `CLOSERS.has(a.name.toLowerCase())`, so Openers/Retention never get a card regardless of role-editor state (user preference, not tied to the role-filter buttons elsewhere in the app); the card's role line always reads "Closer" since only closers reach the render step. `window._agentAllRows` already excludes `TERMINATED`/`INACTIVE_RECENT`, same as every other agent view. ### Recently Inactive Agents (no calls in the last 10 days of the selected range)

When a user runs a report over a date range longer than ~10 days, an agent who stopped taking calls partway through (left the floor, moved teams, etc.) would otherwise still show up in every agent view just because of older activity earlier in the range. `INACTIVE_RECENT` is computed fresh on every `buildDashboard()` run (not hardcoded, not persisted) and excludes those agents the same way `TERMINATED` does.

- Window: `toStr` (the selected range's end date) minus 9 days through `toStr` inclusive = a 10-day window. An agent is flagged `INACTIVE_RECENT` if their latest call in the filtered `calls` set falls **before** that window, i.e. they have zero calls anywhere in the most recent 10 days of the selected range
- If the selected range itself is 10 days or shorter, the cutoff falls before `fromDate`, so every agent's calls are inside the window and nothing is excluded — this only kicks in on longer ranges
- Computed right after the field-normalization pass at the top of `buildDashboard()` (`agentLastCallDate` = per-agent latest call date via `getDateStr(new Date(r._ts))`, compared against `inactiveCutoffStr`)
- Same scope as `TERMINATED`: excluded from Agent Performance table, Agent Call Funnel, Long Calls No Deal, Unassigned Agents, and the coaching-issue callouts in Issues Detected — **not** excluded from overall KPIs, campaign totals, or phone-keyed views (DPC, Incomplete Transfers)
- Implementation: every same `calls.filter(...)` site listed under Terminated Agents above also excludes `INACTIVE_RECENT.has(r._name.toLowerCase())`
- Not part of the Settings role editor and not persisted — recalculated from whatever file/range is currently loaded

## Enrollment Logic

- One enrollment per unique phone number per day
- `Cordoba Enrolled Date` must match the analysis date
- **Agent credit** goes to the agent named in **`Assigned To`** column (if populated); fallback: agent with the latest call timestamp to that phone on that day
- Debt comes from `Enrolled Debt` column on the enrolled row

### Campaign Attribution (separate from agent credit)

- Enrollment is credited to the **campaign of the first call to that phone on that day**
- Rationale: if a lead first came in on TransferK, was transferred to an agent on AGENTDIRECT, and closed on campaign 1000 (agent outbound), it counts as a **TransferK enrollment**
- Campaign `1000` = agent outbound dialer — not a source campaign
- Implementation: `enrolledFirstCallRow[phone]` = the row with the min `r._ts` for that phone; `r._enrolled = true` only when the row IS that first-call row (row identity, not timestamp equality — two rows with tied timestamps can't both be flagged)
- **Agent credit and campaign attribution are independent** — agent credit uses `agentEnrollCredit` (from `enrolledPhoneAgent`), campaign attribution uses `_enrolled` flag on the first-call row

### Enrolled column in Campaign / Queue Breakdown

- `_enrolled` is set on exactly one row per enrolled phone (the first call row)
- This prevents double-counting across campaigns (old bug: every row for the phone had `_enrolled=true`, so every campaign the phone touched counted +1)
- A warning note (⚠️) is shown in the section header — hover it for the full explanation
- The displayed number uses `s.enroll` (raw row count); `s.enrolledPhones` (Set) is used for the clickable phone modal

### Enrolled column in Agent Performance Table

- Uses `agentEnrollCredit[k].count` (unique enrolled phones per agent) — **never** `d.enr`
- `d.enr` is row-based and can be lower than actual credit when `Assigned To` credits an agent whose rows are not the max-timestamp rows
- The phone list shown on click comes from `agentEnrollPhones[k]` — always in sync with `credit.count`
- Implementation: `enr: credit.count, debt: credit.debt` in `buildRowsFromMap` (line ~619)

### Campaign `1000` and Agent Outbound

- Campaign `1000` = agent outbound dialer (closer calls out to client directly)
- It is NOT a source campaign — do not attribute enrollments to it
- If a phone first came in on TransferK, then the closer called back on `1000`, the enrollment belongs to **TransferK**
- This is correctly handled by the first-call attribution rule above

## Pending Deals Without a Cordoba Enrolled Date (CA Escrow / Waiting for Payment)

Two `CRM Status` situations mean a lead has effectively already closed even though `Cordoba Enrolled Date` hasn't been populated yet — both count as a deal now, not just once the enrolled-date column shows up:

| Rule | Condition | Rationale |
|------|-----------|-----------|
| CA escrow | `State==='CA'` (case-insensitive) `&& CRM Status==='Approved'` (case-insensitive, exact match) | CA leads sit in a legally-required 3-day escrow/rescission period before they can be formally enrolled |
| Waiting for payment | `CRM Status` normalizes to `'waiting for first payment'` (case-insensitive, underscores/spaces both accepted, any state) | Deal already closed — just waiting on the first payment to process |

- Folded directly into the existing enrollment pipeline (not a separate KPI): `enrolledPhoneAgent` (built in `runAnalysis()`) treats a row as enrolled if it has a `Cordoba Enrolled Date`/`Enrolled Date` in range **OR** either pending-deal condition above is true — the pending case is dated by the row's own `call_date` (no enrolled-date column exists yet) instead of the enrolled-date column
- `State` is looked up **per-phone, not per-row** (`phoneIsCA` Set, built once from every row for that phone) before combining with `CRM Status` — a dialer export doesn't necessarily stamp `State` on the same row that carries the latest `CRM Status` update, so requiring both on one row missed real CA-approved deals; the same `phoneIsCA` per-phone lookup is used for `anyEnrolledPhone` in `buildDashboard()`
- **Bug fixed (July 2026): wrong column name silently zeroed out every CA escrow deal.** The lookup only checked `r['State']`, but this org's exports carry the column as `CRM_State` — so `phoneIsCA` was always empty and the CA-escrow branch could never fire for any lead, even ones the CRM UI clearly shows as an approved CA deal (confirmed via a real "Correct Transfers Received" row showing 0 Enrolled despite the underlying lead being CA/Approved). Fixed by checking `r['State']||r['CRM_State']` everywhere `State` is read (`phoneIsCA` build in both `runAnalysis()` and `buildDashboard()`, and `r._state`).
- Entry carries an `escrow:true` flag (`enrolledPhoneAgent[phone].escrow`, set when either condition is true) so pending deals can be distinguished from real Cordoba enrollments; whichever row (real or pending) has the latest timestamp for a phone determines the final agent credit/debt/flag for that phone
- This flows automatically into everything keyed off `enrolledPhoneAgent`/`enrolledPhones`: Total Enrolled KPI, Conv Rate, agent credit (`agentEnrollCredit`)/Agent Performance Enrolled column, campaign attribution (`_enrolled` flag via `enrolledFirstCallRow`)
- `window._pendingDealPhones` = `Set` of every phone flagged `escrow:true` in `enrolledPhoneAgent`, built once per `buildDashboard()` run. **Long Calls, No Deal** (`renderLongNoDeal()`) excludes a phone from `longNoConvert` if it's in `pendingPhones` **regardless of which agent the enrollment credit landed on** — the closing/approval call is often a later follow-up by a different agent (or `Assigned To` points elsewhere) than the one who made the original long call, so per-agent `agentEnrollPhones` subtraction alone was missing these
- `anyEnrolledPhone` (used by DPC/Incomplete Transfers/Received Transfers/Ytel Discrepancy to check "has this phone ever enrolled") also treats both pending-deal conditions as enrolled, so a pending deal's SALE row won't be flagged as a Ytel Discrepancy and its phone is treated as an enrolled client in those sections
- `r._state` = `(r['State']||'').trim()` — normalized alongside `r._crmStatus` in `buildDashboard()`
- Total Enrolled KPI subtitle shows `incl. N pending (CA escrow / waiting for payment)` when `pendingEnrolledCount>0`, otherwise the original `with Cordoba Enrolled Date` text
- `Enrolled Debt` on pending-deal rows is typically empty/0 (the deal isn't formalized in Cordoba yet) — this is expected, not a bug
- **Bug fixed (July 2026): wrong string format silently zeroed out every "waiting for payment" pending deal.** The check compared `crmStatus==='waiting_for_first_payment'` (snake_case, underscores) — but this org's CRM Status values (confirmed via the modal pills in the app, which render `r.crmStatus` with zero text transformation) actually come back space-separated, e.g. "Waiting for First Payment". An exact-match against the underscore form never matched real data, so this pending-deal rule never fired for anyone — a closer could make a genuine closing outbound call, the lead's CRM Status could read "waiting_for_first_payment" in the UI, and the agent would still show `enr:0`/`Conv%: —`. Fixed by normalizing both sides before comparing: `crmStatus.replace(/_/g,' ').replace(/\s+/g,' ').trim()==='waiting for first payment'` (in both `runAnalysis()`'s `enrolledPhoneAgent` build and `buildDashboard()`'s `anyEnrolledPhone` build) — now matches either `waiting_for_first_payment` or `waiting for first payment`. The CA-escrow `crmStatus==='approved'` check is unaffected (single word, no separator to normalize).
- **Bug fixed (July 2026): stale CRM Status re-minting duplicate enrollments.** `CRM Status` often doesn't get cleared/updated once a deal actually closes — a phone can sit at `waiting_for_first_payment` (or CA `Approved`) for days after its real `Cordoba Enrolled Date`. Any later call to that phone (e.g. a Retention follow-up) would re-trigger the pending-deal branch and get counted as a **second, new** enrollment dated by that later call, credited to whoever made it — even though the phone already enrolled days earlier. Fixed by building `realEnrolledPhones` in `runAnalysis()` — a Set of every phone with a real, parseable `Cordoba Enrolled Date`/`Enrolled Date` **anywhere in the full uploaded file** (`mergedRaw`, not just the selected date range) — and gating `isPendingDeal` on `!realEnrolledPhones.has(phone)`. A phone that has ever really enrolled can no longer be re-flagged as a pending deal on a later day.
- **Bug fixed (August 2026): an old, unrelated enrollment made a genuinely-pending phone show as "not converted" in Long Calls, No Deal.** The `realEnrolledPhones` guard above is a blunt Boolean — "has this phone *ever* really enrolled" — with no sense of time. A real example: a different agent enrolled a phone weeks earlier (a real Cordoba Enrolled Date on file). Later, Alex Tambouly made a 30+ minute call to the *same* phone that genuinely moved it to `Waiting for First Payment`. The guard saw the old enrolled date and silently discarded that pending status: the phone never entered `enrolledPhoneAgent`, never joined `_pendingDealPhones`, so Alex's call showed up as "not converted" despite the CRM Status on screen literally reading "Waiting for First Payment". **Scoped fix, explicitly requested this way**: enrollment credit must NOT shift to whoever made the pending-status call — credit stays exactly as before (`Assigned To`/latest-real-enrollment-touch), `realEnrolledPhones` and `enrolledPhoneAgent` in `runAnalysis()` are untouched. Instead, a new credit-independent set — `window._currentlyPendingPhone`, built in `buildDashboard()` right after `phoneLatestCrmStatus` — flags a phone if its *most recent known CRM Status in the current range* (regardless of realEnrolledPhones, regardless of which agent touched it) currently reads CA-escrow-Approved or Waiting-for-First-Payment. `renderLongNoDeal()`'s `pendingPhones` is now the union of `_pendingDealPhones` (credit-scoped, unchanged) and `_currentlyPendingPhone` (the new, credit-independent signal) — so a phone at a genuinely current pending status is excluded from "not converted" in this one card only, without touching Total Enrolled, Conv Rate, or any agent's credit anywhere else in the app. (An earlier version of this fix changed `isPendingDeal` itself, which incorrectly shifted enrollment credit to whoever made the later call — reverted per explicit user correction.) **Known residual risk, accepted on purpose:** this uses "most recent known status within the current range" as the only available freshness signal — if a phone's CRM Status is never touched again after a real enrollment (not even once, ever), a stale pending status on a much later call could still slip through, narrowing but not eliminating the July 2026 "stale CRM Status re-minting duplicate enrollments" bug. No stronger signal (an actual CRM Status last-modified timestamp) exists in the export to fully resolve this.

## Hourly Breakdown Logic

- **Unique #s per hour** — phone counted in the hour of its **first call of the day**
- **Enrolled per hour** — credited to the **hour** of the agent's **last call to that enrolled phone** (hour placement is agent-scoped)
- **Enrolled per hour — which campaign bucket** — uses `enrolledFirstCallRow[phone]._campaign` (the same first-call-of-enrollment-day campaign attribution as the Campaign/Queue Breakdown card's `_enrolled` flag), **not** the campaign of the agent's own last call. This keeps the Agent Performance campaign filter consistent with the Campaign Breakdown card for the same phone.
  - **Bug fixed (July 2026)**: previously the hour AND the campaign bucket both came from the agent's own last call to the phone (`agentPhoneLastCall[agent][phone].camp`). Since an agent's own last touch to a phone can be on a different campaign than the one that gets true attribution credit (e.g. lead came in on TransferK, closer's last touch was an outbound call on `1000`), the Agent Performance campaign filter could disagree with the Campaign Breakdown card for the same phone/agent.
  - Implementation: in the `agentEnrollPhones` hourly-crediting loop (`buildDashboard`), `attribCamp=enrolledFirstCallRow[phone]&&enrolledFirstCallRow[phone]._campaign` replaces `last.camp` when deciding which `agentHourCampMap` bucket to credit; the `(campaign, agent, hour)` entry is created on demand if the agent has no personal calls tagged with that campaign.
  - Known remaining gap: the Agent Performance summary row's top-level `Enrolled`/`Debt`/phone-list still use the agent's **global** `agentEnrollCredit` (all campaigns) even when a campaign filter is active, so the summary row can still show a higher total than the sum of its own hourly sub-rows. Not yet fixed — flagged for a follow-up change.

- **High alert badge**: every row in this list already means zero follow-up of any kind happened after the drop (per the flagging rule above), which implies no outbound call was ever made either. Each row shows a ⚠️ badge before the phone number (tooltip: "High alert — no outbound call was ever made to this phone after the drop"). Implemented in the `rowHtml` template inside `renderDpcDrops()`.

## Incomplete Transfers (CLtrns with no inbound follow-up)

Flags calls dispositioned `CLtrns` (Call Center Transfer) where the transfer never actually landed with another agent — the opener marked it as transferred but no one on the receiving end ever picked it up. Card `#badTransferCard`, styled like the DPC card (red title, campaign multi-select filter, Enrolled Clients vs Other Calls split), placed directly after the DPC card.

- **Per-event logic**: for each `CLtrns` event on a phone, check if any call with `direction === 'inbound'` (any status, any campaign) occurred on that phone after the `CLtrns` timestamp
- If no later inbound call exists → flagged. This mirrors a real transfer: a genuine hand-off produces a new inbound call into the closer's queue (e.g. `AGENTDIRECT`); if that never happens, the "transfer" never actually landed
- Rule was confirmed against two real examples: (1) opener dispositions `CLtrns`, no other row for that lead at all → flagged; (2) opener dispositions `CLtrns` on `TransferK`, later an agent has an inbound call on `AGENTDIRECT` for the same phone → correctly not flagged
- Scope: any agent's `CLtrns` dispo is checked, not just agents in the `OPENERS` set (a closer or untagged agent could also mis-use the status)
- Implementation: `cltrnsEvents[phone]` = all CLtrns timestamps+sec+recording; `inboundTs[phone]` = timestamps of all inbound calls (any status) to that phone; flag if any CLtrns event has no later inbound call
- `badTransferFlagged[phone].recs` collects `{phone,sec,recording,crmStatus}` for each unfollowed CLtrns event → surfaced as `badTransferData[].records`
- **Click phone to play/download recording**: same shared `showFlaggedPhones(d.records, d.phone+' — Incomplete Transfer')` modal used by DPC and Long Calls, No Deal

### Correct Transfers Received by Agent

Card `#receivedTransferCard`, placed directly after the Incomplete Transfers card. Shows, per receiving agent, how many `CLtrns` transfers actually landed with them.

- For each `CLtrns` event that is NOT flagged as incomplete (i.e. it has a later inbound call), credit goes to the agent on the **first** inbound call after that event's timestamp — that's the agent who actually picked up the transferred lead
- Implementation: `inboundCalls[phone]` = all inbound calls (any status) with `{ts, agent, camp, sec, recording}`, sorted by `ts`; for each `cltrnsEvents[phone]` entry, `followUps.find(f=>f.ts>ev.ts)` gives the receiving call

- `receivedTransferRows[].notEnrolledRecords` = `d.records.filter(rec=>!d.enrolledPhones.has(rec.phone))` — the received-transfer call records whose phone never enrolled, computed at render time (not stored on `receivedTransfers[agent]` itself)

## Agent Performance Table

Time bracket columns (in order): Short% ≤30s | <2 min | **1–2 min** | 5–10 min | 10–15 min | 15–20 min | 20–30 min | 30+ min | Avg Talk | Total Talk | Enrolled | Debt $ | Conv%

### Conv% (enr/unique >2m)

`Conv% = pct(a.enr, gt2mUniq)` — `a.enr` (unique enrolled phones credited to the agent) ÷ `gt2mUniq` (unique **phones** the agent had at least one call ≥120 sec with), shown as `—` if either side is 0.

- **Bug fixed (July 2026): denominator counted raw calls, not unique phones, while the numerator was already unique-phone — the two sides weren't measuring the same unit.** The formula used to be `enr / gt2m`, where `gt2m` was a per-row counter (`d.gt2m++` on every call ≥120 sec, no phone dedup) — so a single phone called 3 times, each over 2 minutes, added 3 to the denominator even though it's one lead. That understated Conv% for any agent making repeat long calls to the same numbers (exactly the "call came in, agent called back and talked 30 min" pattern), since the numerator (`enr`) only ever counts that phone once. Fixed by adding a `phonesGt2m` Set alongside the existing `gt2m` counter everywhere calls are bucketed by agent — `agentMap` (global), `agentDirMap` (per direction), `agentCampDataMap` (per campaign) — populated by `if(r._sec>=120) phonesGt2m.add(r._phone)` next to the existing raw counter. `gt2m` itself is untouched (still used by the bracket-% cells like `funnelCell(a.gt2m,...)` elsewhere, unrelated to Conv%). All three places that compute this ratio — the main Agent Performance table (`renderAgentBody`'s `convPct`), the Agent Management Board (`renderTransferLeaderboard`'s `convPct`), and the Agent Report Card PDF (`exportAgentReportCards`'s `convPct`) — now use `(a.phonesGt2m?a.phonesGt2m.size:0)` as the denominator instead of `a.gt2m`. Column headers updated to `Conv% (enr/unique >2m)` (was `Conv% (enr/>2m)`) to make the unit explicit, matching the naming the Campaign/Queue Breakdown table already used for its own total-vs-unique split (`Conv% (enr/total >2m)` / `Conv% (enr/unique >2m)`).
- **Bug fixed (July 2026): follow-up calls to already-enrolled clients dragged down Conv% with no way to offset it.** Agent credit (`enr`) for an enrollment is dated by when the deal actually enrolled and attributed to whoever made the latest call **on that enrollment day** — so a later call to the same phone by a different agent, on a different day, never earns numerator credit no matter how long it runs, even though it's a real `CC` ("Current Client") service/retention call, not a sales attempt. Before this fix, that same call still counted toward the agent's `>2min` denominator (since duration is the only thing checked there), which could only ever hurt Conv%, never help it — a real example: a closer's 16-minute outbound call to a lead that had already enrolled 6 days earlier showed `Enrolled: 0` and `Conv%: —` for that closer, purely because the call landed in the denominator with zero chance of a matching numerator credit. Fixed by excluding a phone from `phonesGt2m` when `anyEnrolledPhone.has(phone) && !enrolledPhoneAgent[phone]` — i.e. the phone shows *some* enrollment signal (a real Cordoba Enrolled Date or a pending-deal CRM Status, checked without a date-range restriction) but did **not** get a credited enrollment entry for the currently selected date range, meaning the enrollment belongs to a different report window. Computed once per row (`alreadyEnrolledElsewhere`, right at the top of the per-row loop in `buildDashboard()`) and applied to all three `phonesGt2m` Sets (`agentMap`, `agentDirMap`, `agentCampDataMap`). A phone that enrolls **within** the currently selected range is unaffected — it still counts in both the numerator and the denominator, since `enrolledPhoneAgent[phone]` exists for it and the exclusion never triggers. Only the agent-level Conv% denominators were changed — the Campaign/Queue Breakdown table's own `Conv% (enr/total >2m)` / `Conv% (enr/unique >2m)` columns (a different, campaign-aggregated `phonesGt2m` in `campMap`/`campDirMap`) were not touched, since that wasn't reported as an issue and is a different metric scope.

### Sticky header row + sticky Agent column (added August 2026)

Design-review finding: the table has 18 columns and can run to dozens of agent rows, so reading one agent's full row required scrolling both vertically (past the header) and horizontally (past the Agent name column) at once — the single highest-risk spot for misreading a number. Fixed with zero data/logic changes, scoped to `#agentTable` only (every other table in the app keeps its normal page-level scroll):

- `#agentTblWrap` (new `id` on the `.tbl-wrap` div wrapping just this table) gets `max-height:70vh;overflow:auto` instead of relying on the shared `.tbl-wrap{overflow-x:auto}` rule. This is required, not cosmetic — `position:sticky` sticks within whichever ancestor actually scrolls, and an ancestor with only `overflow-x` set never scrolls vertically (per the CSS overflow-x/overflow-y computed-value pairing), so a sticky header on `.tbl-wrap` alone would silently do nothing. Boxing the table with its own scroll area is the standard fix and also means a long agent list no longer inflates the whole page's scroll height.
- `#agentTable thead th{position:sticky;top:0}` + `#agentTable thead th:first-child{left:0}` keep the column-label row and the top-left corner cell in view while scrolling down.
- `#agentTable tbody td:first-child{position:sticky;left:0;background:var(--surface)}` keeps the Agent name column in view while scrolling right; a `:hover` rule and a `.agent-hour-row` rule override that default background to match the row's own background (`var(--gray-50)` for hour sub-rows) so the sticky cell doesn't show a color seam. The TOTAL row's first `<td>` gets its matching background (`var(--gray-100)`) set inline (in `renderAgentBody()`, next to the row's existing inline `background`) since it's a single one-off row, not a reusable class.
- Verified via `getBoundingClientRect()`/`getComputedStyle()` in a live browser session (both axes independently, plus all three background-override cases) rather than by eye — the sandboxed preview tool used during this review doesn't correctly composite `position:sticky` elements mid-scroll in its screenshot capture (a snapshot-rendering limitation, not a rendering bug in the page itself).

The `Inbound`/`Outbound` unique-phone-count cells in the agent main row are clickable (same shared `#enrollModal` used elsewhere), opening a list of that agent's phones in that direction bucket with CRM Status and Enrolled Debt per number.

- Direction bucketing matches what's already displayed in the count (`agentPhoneFirstDir[name+'||'+phone].dir` — the direction of the phone's **first** call to that agent), so the modal list always matches the number shown
- `agentPhoneDetail[name][phone]` — built in the same per-row loop as `agentMap`/`agentDirMap` (line ~2210), keeps the CRM Status (`r._crmStatus`) AND Ytel status (`r._status`, from the `status` CSV/XLSX column, e.g. SALE/DNC/DROP/CLtrns) from whichever row has the latest `r._ts` for that phone. No longer consumed by the Inbound/Outbound phone-list modal (see bug-fix note below) — left in place, cheap to reuse later.
- Each agent row (`agentRows` in `buildDashboard`) carries `inboundPhones`/`outboundPhones` arrays of `{phone, crmStatus, ytelStatus, debt, enrolledDate, recording, sec}` — `debt`/`enrolledDate` come from `enrolledPhoneAgent[phone].debt`/`.enrolledDate` (both blank/0 if the phone never enrolled)
- `enrolledPhoneAgent[phone].enrolledDate` (added July 2026) — the `ds` date string already computed in `runAnalysis()`'s enrollment loop (either the real `Cordoba Enrolled Date`, or the pending-deal's `call_date` fallback when there's no enrolled-date column yet), stored alongside `agent`/`ts`/`debt`/`escrow` so callers don't need to re-derive it. `showPhoneCrmList()` renders it as a green "Enrolled `<date>`" pill next to the CRM Status pill whenever `r.enrolledDate` is non-empty — currently only the Inbound/Outbound phone-list modal populates this field; other `showFlaggedPhones()` callers (DPC, Incomplete Transfers, Long Calls No Deal, etc.) don't set it yet and simply omit the pill

## Date Parsing (`getDateStr`)

- Date objects at UTC midnight → use `getUTCFullYear/Month/Date` (date-only cells like `Cordoba Enrolled Date`)
- Date objects with time → use local `getFullYear/Month/Date` (datetime cells like `call_date`)
- Strings: match `YYYY-MM-DD` or `M/D/YYYY`

## Normalization Conventions

- `r._ts` = `parseTs(call_date)` — parsed **once** in the normalization pass at the top of `buildDashboard()`; every later loop (missed callbacks, DPC, CLtrns, received transfers, agent first/last-call maps) must reuse `r._ts`, never re-call `parseTs`
- `r._hour` is derived from `r._ts` (`new Date(r._ts).getHours()`, zero-padded) so it works for Date objects (`cellDates:true`) and `M/D/YYYY` strings alike; falls back to the old `String(...).slice(11,13)` only when the timestamp is unparseable
- `attrJson(v)` (defined next to `fmt$`) must be used instead of `JSON.stringify` whenever JSON is embedded in a single-quoted inline `onclick='...'` attribute — it entity-escapes `&`, `'`, `<` so agent/campaign names containing apostrophes don't truncate the attribute
- Table bodies with a TOTAL row are built as one string (`agentRowsHtml`/`campRowsHtml`) and assigned to `innerHTML` once — no `innerHTML +=` (it re-parses the whole table)
